# 角色手册：开发（PP = Android / Wewe = Web）

> 前置：已按 `CLAUDE.md` 完成开工四步。本手册只写你这个岗位的动作序列。
> 铁律一句话：**只按 `authority/` 落地，不发挥；先报问题，再动手；逐条交付，不汇总。**

---

## 一次领多少

**3~5 条**。少于 3 条浪费启动开销，多于 5 条必然缩水。
一个会话可以做 3~5 条，但**必须是独立条目、独立回报、独立复现**——原子性在记账上，不在会话上。

---

## 动作序列

### 第 1 步：pre-flight（写第一行代码之前，必须做完）

对领到的**每一条**：

1. 打开条目里引用的 authority 章节（文件 + 章节号），**逐条读完**，不许跳读
2. 对照当前实现，判断该章节**是否足以支撑落地**
3. 把下列任一情况写进该条目并**停下**：
   - **缺失**：权威没规定这个场景
   - **冲突**：两处权威互相矛盾（写清哪两处）
   - **不合理**：按权威做会明显出问题（说明为什么）
   - **歧义**：一句话有两种以上实现方式（列出你看到的几种）
4. 全部条目 pre-flight 完成后，**统一回报，等裁决**

**要点：**
- pre-flight 的产出是**问题清单**，不是"我读了"。**空手回报"无问题"，之后又冒出理解分歧的，判 pre-flight 失败，整条打回**
- 条目里写的任何数值、逻辑描述**都不作数**，一切以 authority 原文为准
- 权威没写的，**不许按理解补、不许参考另一端、不许沿用旧实现**——报缺失，等裁决

### 第 2 步：改（拿到裁决后）

- 一条一条改，**一条一提交**，提交信息写清改了什么、对应哪条权威
- 只碰条目"范围"里写明的文件；越界即返工
- Web 不碰 Android，Android 不碰 Web

### 第 3 步：复现验证（每条都要做）

**顺序不能反：**

1. **改之前**先复现现象（复现不出来的，回报"无法复现"，不许硬改）
2. 改完**再复现一次**，证明现象消失
3. Web：本地 `node web/serve.js`，用左下角版本水印确认跑的是自己这一版
4. Android：不需要截图，但要写清"改了什么、期望在实机上看到什么变化"，由 Ant 实机验

**不算证据的**：我读了文档 / 我分析了 / 我改了代码 / 我自测了 / 代码里已经有了

### 第 4 步：逐条回报 + push

在**每一条自己的条目下**追加一行，三选一：

- `已改：<改了哪个文件的什么> | 依据 <权威章节> | 复现：<改前现象→改后现象>`
- `未改：<原因>`
- `不适用：<理由>`

**回报行数必须等于任务条数。对不上直接判失败，不看内容。**

最后 `git push`。**push 成功才算完成**——板上写完成但代码没推，算事故。

---

## 禁止清单

- ❌ 自评"已通过 / 已验收"——你只能报"已改，待验"，合格与否只有 Ant 判
- ❌ 把"通过"写进 authority 文档或任务板状态
- ❌ 静默缩范围（任务说四个页面只做一个）——少做必须写出来等裁决
- ❌ 汇总回报（"N 条全部修复"）
- ❌ 改 authority、复制 authority 内容到别处
- ❌ 新建过程文件（dev_reply / 报告 / 评审）
- ❌ 无任务碰 `story-data/`、`assets/bg/`、`assets/main pic/`、`android/app/src/main/res/`

## 结论要标证据等级

`【已验证】`（附命令 / 文件行号 / 实测结果）或 `【推断】`（附待验方式）。
别人的回报、历史报告里的猜测，引用时保留原等级，**不得升格为事实**。
